# TradeTrail 项目方案与实施状态

文档核对日期：2026-10-29。本文件统一维护项目范围、业务约束、实施状态和验收记录。功能介绍见 [README](../README.md)，具体架构见[后端设计](design/TradeTrail-后端设计文档.md)。文档更新不代表重新执行了业务验收，历史数量以第 6 节标明的日期为准。

## 1. 项目定位与边界

TradeTrail（商迹）面向单个店家，提供用户商城、店家管理台和独立物流模拟端，串联商品、购物车、订单、模拟支付、履约、售后和退款。

当前范围为单店、单币种、单仓、单包裹、按商品购买、整单退款。商品直接以 `product_id` 标识交易和库存单位，没有独立的多规格 SKU 模型。金额使用整数分，不包含优惠券、优惠分摊、运费计算或部分退款。支付和退款均为 mock，不发生真实资金交易。

| 入口 | 技术与角色 | 业务边界 |
|---|---|---|
| 用户商城 | Vue 3、TypeScript、Vant、Pinia；`CUSTOMER` | 商品浏览、购物车、结算、付款、订单物流、收货和本人售后 |
| 店家管理台 | Vue 3、TypeScript、Element Plus、Pinia；`MERCHANT_ADMIN` | 商品、库存、发货、售后审核和异常恢复 |
| 物流模拟端 | 独立 Spring Boot、Thymeleaf；`LOGISTICS_OPERATOR` | 录入运单节点、签名推送、自动及人工重试 |

商城是 Maven 多模块单体。物流服务独立运行、独立存储，通过 HTTP 推送，不读取商城数据库。账号是本地演示账号，没有注册、密码管理或完整生产身份体系。

## 2. 当前实施状态

| 领域 | 已实现 | 当前限制 |
|---|---|---|
| 商品 | 新建、编辑、上下架、改价、库存调整及原因记录 | 无多规格 SKU、图片上传与多店铺模型 |
| 购物车 | 加购、改量、勾选、删除、报价和结算 | 商品价格及可售量以结算时服务端校验为准 |
| 订单 | 多明细、地址和成交快照、状态机、版本及状态日志 | 无拆单、部分取消 |
| 库存 | 可售/预留/已售、预留转换、条件更新、流水 | 单仓模型，未建设库存对账后台 |
| 支付 | 单订单支付尝试、异步签名通知、幂等、关单与迟到支付补偿 | 仅 mock；无真实渠道查询、额外收款模型或运行时渠道切换 |
| 履约 | 唯一模拟运单、轨迹、乱序摘要保护、确认及自动确认 | 单包裹；物流异常尚无独立工单 |
| 售后 | 申请冻结履约、审核、退货运单、验收、整单退款、失败重试 | 每单一个工单；没有寄回超时自动终止 |
| 集成 | outbox/inbox、租约恢复、退避、失败队列和人工恢复 | 未提供消息队列、查询投影或独立事件订阅 |
| 工程 | H2 隔离测试、MySQL 集成、架构检查、浏览器测试和 CI 配置 | 完整生产验收、容量和多实例故障验证尚未完成 |

列表存在全量读取后分页或页面筛选的实现，不能以参数支持 `page/size` 推断已完成数据库分页。Redis 仅是 Compose 可选服务，业务尚未使用；项目没有引入消息队列或 Spring Modulith。

## 3. 完整交易链

1. 店家创建商品、设置初始库存并上架。
2. 用户加购，确认数量、期望单价和地址；服务端核价并在同一事务中保存快照、预留库存、清理已结算购物车项。
3. 创建支付尝试；模拟收银台保存渠道成功结果及 `PAYMENT_NOTICE`。投递器经签名 HTTP 回调推进待发货，预留转已售。
4. 店家发货时锁定订单、检查状态及售后冻结，再生成 `MOCK-...` 运单。
5. 物流服务先保存节点及待推送记录，再签名推送。商城保存轨迹，重复事件去重，迟到节点不倒退摘要。
6. 用户在发货后可主动确认；自动确认要求妥投达到配置天数且没有售后冻结。
7. 申请售后立即冻结履约。未发货批准后退款；已发货或完成的订单需要寄回、验收，再退款。
8. 未发货仅退款在退款成功后回补；退货质检合格时回补，不合格不回补。退款失败沿用原退款号重试，避免重复回补。

## 4. 必须保持的交易约束

### 4.1 下单与库存

- 商品价格、上架状态、库存及身份由服务端确认。订单快照不随商品后续修改而变化。
- 多商品按 `productId` 升序处理，降低锁顺序不一致的风险；任何一项失败，订单及先前预留整体回滚。
- `stock` 保存 `available/reserved/sold`；`inventory_reservation` 保存每单每商品的 `RESERVED/CONFIRMED/RELEASED/RESTOCKED`。
- 下单 `available → reserved`，支付确认 `reserved → sold`，未付关闭 `reserved → available`，符合条件回补 `sold → available`。
- 条件更新、预留状态转换和唯一流水共同防止负库存和重复执行。不能用 Redis 数量替代数据库事实。

### 4.2 状态与幂等

- 主订单状态及守卫统一由 `OrderState` 定义；售后冻结、支付和物流状态独立保存。
- 成功业务写请求由 HTTP 幂等记录重放；同一用户同一键不能更换方法、路径或原始 JSON。
- 前端网络错误时保留原键。支付与物流回调另有通知去重和业务再校验，不能只依赖浏览器按钮禁用。
- 支付、关单、发货和售后在修改前锁定订单。订单更新检查预期状态及版本，写入审计日志。

### 4.3 支付与恢复

- 浏览器确认模拟付款只登记渠道结果，不能直接视为订单已付款。
- 待支付订单的有效通知推进待发货；已未付关闭订单到账后标记 `LATE_PAYMENT` 并补偿退款，不重开订单、不再次占库存。
- 每订单一笔支付尝试、每支付一笔整单退款，受数据库唯一约束限制；真实支付的多次尝试和不确定结果仍需另行设计。
- 业务事实与 outbox 同事务保存。投递可能重复，处理器必须检查已处理事实和当前状态，不能承诺外部效果“恰好一次”。
- 应用和数据库使用 UTC；无时区物流发生时间按 UTC 解释，页面转换为本地时间。

## 5. 实施阶段与后续工作

| 阶段 | 状态 | 后续重点 |
|---|---|---|
| M0 模块与运行骨架 | 已实现 | 保持依赖边界和独立数据库 |
| M1 商品、购物车与快照 | 主流程已实现 | 数据库分页、大数据量验证 |
| M2 订单、库存与状态机 | 已实现并有并发回归 | 扩大竞争场景与故障验证 |
| M3 模拟支付与补偿 | 已实现 | 真实渠道合同、查询和不确定结果处理 |
| M4 履约与售后 | 主流程已实现 | 寄回超时、物流异常工单 |
| M5 工程与交付 | 部分完成 | 容量报告、多实例、进程故障及存量数据迁移演练 |

待完成或待专项验收：

- [ ] 生产容量、延迟与资源占用报告；现有并发用例只证明特定场景的正确性。
- [ ] 多实例、租约过期并发处理、强杀进程后的恢复演练。
- [ ] 真实存量数据库的升级与备份恢复演练。
- [ ] 独立物流服务在真实 MySQL 上的专项恢复测试。
- [ ] 退货寄回超时自动终止、物流异常独立工单。
- [ ] 真实支付退款、渠道结果查询与动态渠道可用性。
- [ ] 列表查询全面下推数据库分页。
- [ ] 逐接口核查测试拆分类和拒绝分支，落实 Agent 规范；现有部分测试仍按一组接口组织。

新增需求先确定业务状态、数据所有权、事务及失败恢复，再实现接口和页面；不为扩展预先堆叠模块或依赖。
