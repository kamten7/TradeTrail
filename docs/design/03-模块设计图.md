# TradeTrail 模块、存储与接口

核对日期：2026-10-29。业务转换见[状态机](01-订单状态机.md)，调用链见[后端设计](TradeTrail-后端设计文档.md)。以下为当前实现，不预设真实渠道或额外服务。

## 1. 工程模块

| 模块/目录 | 内容 | 运行方式 |
|---|---|---|
| `tradetrail-domain` | 领域记录、状态机、存储和渠道端口 | 普通 JAR，不单独启动 |
| `tradetrail-application` | catalog/cart/order/inventory/payment/fulfillment/after_sale/integration 用例 | 普通 JAR |
| `tradetrail-persistence` | MyBatis-Plus、Mapper SQL、端口适配器 | 普通 JAR |
| `tradetrail-api` | 按角色与资源组织的 Controller、安全、幂等、错误响应 | 普通 JAR |
| `tradetrail-channel-mock` | 模拟支付及通知、物流协议适配器 | 普通 JAR |
| `tradetrail-boot` | 商城装配、任务、迁移及集成测试 | 可执行 JAR，默认 8080 |
| `tradetrail-logistics-simulator` | 独立页面、账号、迁移、事件投递和恢复 | 可执行 JAR，默认 8081 |
| `frontend/customer` | 用户 Vue 应用，Vant、Pinia | Vite 默认 5173 |
| `frontend/merchant` | 店家 Vue 应用，Element Plus、Pinia | Vite 默认 5174 |
| `frontend/shared` | 请求、错误、幂等重试、模型和图标 | 由两端源码引用 |
| `frontend/tests` | Playwright 验收 | 独立依赖位于 `frontend/package.json` |

根 Maven 管理 7 个模块。Compose 仅提供 MySQL 与可选 Redis；不会自动启动上述应用。版本和启动命令见 [README](../../README.md)。

## 2. 数据结构

| 表 | 事实及关键约束 |
|---|---|
| `product` | 名称、描述、整数分售价、上架状态 |
| `stock` | 每商品可售、预留、已售和版本 |
| `stock_adjustment` | 初始库存或人工调整数量、原因、操作者 |
| `cart_item` | 用户购物车、商品、数量及选中状态 |
| `sales_order` | 用户、总额、主状态、版本、冻结、地址、付款期限及完成时间 |
| `order_item` | `(order_id, product_id)` 主键，商品名、数量、成交单价快照 |
| `inventory_reservation` | 每单每商品数量和转换状态 |
| `stock_ledger` | 订单库存动作，`(order_id, product_id, action)` 唯一 |
| `order_status_log` | 前后状态、事件、操作者、命令、traceId、时间 |
| `idempotency_record` | 唯一命令键、请求指纹、成功响应状态及正文 |
| `payment_attempt` | 单订单唯一支付尝试、渠道、金额、处理与渠道状态 |
| `payment_notice` | 回调去重及对应订单 |
| `refund_attempt` | 单支付唯一整单退款，原因、售后关联、次数与错误 |
| `shipment` | 单订单一张发货单，唯一运单、摘要、进度和妥投时间 |
| `tracking_event` | 事件 ID、运单、状态、地点、发生及接收时间 |
| `after_sale_case` | 单订单售后、类型、状态、审核理由、退货运单及回补标记 |
| `after_sale_action` | 售后审核、验收及退款完成的审计动作 |
| `outbox_event/inbox_event` | 持久化待投递事实、消费去重 |
| `sim_tracking_event`（物流库） | 物流事件、投递状态、次数、租约、错误及下次时间 |

完整列定义以[商城迁移](../../tradetrail-boot/src/main/resources/db/migration)和[物流迁移](../../tradetrail-logistics-simulator/src/main/resources/db/migration)为准。V3 为旧表加入交易记录及演示回填，不能把回填记录当作真实渠道凭证；真实存量升级尚需专项演练。不要修改已在目标库执行的历史迁移。

## 3. 商城 HTTP 接口

下面是后端实际路径；浏览器另加 `/api` 并由代理移除。业务写请求需要 Session、CSRF 和 `Idempotency-Key`，回调使用服务间签名。分页从 0 开始，具体支持范围以 Controller 为准。

| 角色 | 方法与路径 | 用途 |
|---|---|---|
| 会话 | `GET /session`、`POST /login`、`POST /session/logout` | 身份、CSRF、登录和退出 |
| 公开商品 | `GET /products`、`GET /products/{id}` | 上架商品查询 |
| 用户购物车 | `GET /cart/items`、`GET /cart/quote` | 明细及选中报价 |
| 用户购物车 | `POST /cart/items`、`PUT /cart/items/{id}`、`DELETE /cart/items/{id}` | 加购、修改及删除 |
| 用户结算 | `POST /cart/checkout`、`POST /orders` | 购物车结算或直接下单 |
| 用户订单 | `GET /orders`、`GET /orders/{id}`、`GET /orders/{id}/history` | 本人订单及状态日志 |
| 用户订单 | `POST /orders/{id}/cancel`、`POST /orders/{id}/confirm` | 取消或确认 |
| 用户支付 | `POST /orders/{id}/payments`、`GET /orders/{id}/payments` | 创建尝试、查询支付与退款 |
| 用户收银台 | `POST /mock/checkout/{paymentId}/complete` | `{success}` 登记模拟渠道结果 |
| 用户物流 | `GET /orders/{id}/tracking`、`GET /orders/{id}/shipment` | 本地轨迹及运单摘要 |
| 用户售后 | `POST /orders/{id}/after-sales`、`GET /orders/{id}/after-sales` | 申请和查询 |
| 用户退货 | `POST /after-sales/{id}/return` | `{trackingNo}` 提交退货运单 |
| 店家商品 | `GET /admin/products`、`POST /admin/products`、`PUT /admin/products/{id}` | 查询、创建及编辑 |
| 店家商品 | `POST /admin/products/{id}/publish` | 上架；下架通过上述 PUT 更新 `published=false` |
| 店家库存 | `POST /admin/products/{id}/stock-adjustments` | `{delta, reason}` 调整库存 |
| 店家订单 | `GET /admin/orders`、`POST /admin/orders/{id}/shipments` | 订单查询及发货 |
| 店家售后 | `GET /admin/after-sales`、`POST /admin/after-sales/{id}/decisions` | 查询及 `{approve, reason}` 审核 |
| 店家验收 | `POST /admin/after-sales/{id}/receipts` | `{qualified}` 质检及退款 |
| 店家恢复 | `GET /admin/refunds/failed`、`POST /admin/refunds/{id}/retry` | 失败退款同号重试 |
| 店家恢复 | `GET /admin/outbox`、`POST /admin/outbox/{id}/retry` | 耗尽自动重试事件的人工恢复 |
| 集成回调 | `POST /callbacks/payments/mock`、`POST /callbacks/logistics/mock` | 签名通知 |
| 物流接收查询 | `GET /callbacks/logistics/mock/status/{eventId}` | 已接收事件查询；当前安全配置允许匿名访问 |

下单体为 `items: [{productId, quantity, expectedPriceCents}]` 和 `address`，不支持旧单商品请求体。错误响应包含 `code/message/traceId/currentStatus/allowedActions`；安全过滤层错误也通过 JSON 返回，不能仅根据页面按钮判断操作权限。可复制示例见[测试与调试](../testing.md)。

## 4. 回调协议

### 支付

`MockPaymentGateway` 将 outbox 支付通知发送到商城配置的回调目标。请求使用 `X-Payment-Timestamp` 和 `X-Payment-Signature`，HMAC-SHA256 原文为 `timestamp + "." + 原始 JSON`。通知包含事件 ID、支付号、金额和结果，验签后再校验渠道成功事实与订单状态。

### 物流

物流 JSON 包含 `eventId/trackingNo/status/location/occurredAt`，请求头为 `X-Logistics-Timestamp` 和 `X-Logistics-Signature`，同样按原始正文计算 HMAC-SHA256。共享密钥从两服务配置读取，浏览器不持有服务间密钥。时间窗口以适配器实现为准，两服务保持时钟一致。

物流操作端使用 `GET /` 展示页面，`POST /events` 创建事件，`POST /events/{eventId}/retry` 人工重试；使用独立 Session 与 CSRF，不要求商城业务幂等键。物流只接受 `MOCK-` 运单及已定义节点，不包含自由文本备注字段。

这些是本项目 mock 合同，不能直接用于描述第三方支付或快递公司的协议。

## 5. 投递状态与重试

| 投递系统 | 状态与处理 |
|---|---|
| 商城 outbox | `PENDING → PROCESSING → SENT`；异常回到 PENDING，8 次失败后 FAILED |
| 物流投递 | `PENDING/RETRY → PROCESSING → SUCCESS`；网络或服务错误退避，达到阈值 FAILED，HTTP 4xx 为 REJECTED |

两者使用 60 秒领取租约、到期扫描和最长 300 秒的退避上限。重试使用原事件 ID，但可重新生成请求时间戳和签名。商城人工队列只展示 FAILED，不包含全部处理中事件；退款失败有独立列表，不能与 outbox 失败混为一谈。

商城事件的 `aggregate_id` 可能是订单号、支付号或退款号，排查时按类型关联。`ORDER_CHANGED` 当前仅登记 inbox 消费事实。多实例下租约和结束写入的完整竞争仍需专项验证，见 [Plan](../Plan.md)。
